NOTES.txt -- vnc.koplugin internals, tests and open ends
==============================================================

This file is for people reading or changing the code. The README is for users.


WHAT THIS IS
------------

An out-of-tree KOReader plugin with both halves of VNC (RFB 3.8): a **client** that renders a
remote desktop through KOReader's BlitBuffer abstraction, and a **server** that serves KOReader's own
screen to any VNC client. Pure Lua + LuaJIT FFI: no build step, no C component, nothing to compile.
The directory is `vnc.koplugin` and its Lua modules live in `vnc/`.


CODE STRUCTURE
--------------

main.lua                  Plugin entry point. Owns the settings store, registers the single
                          file-browser menu entry, keeps the session registry (one Session per
                          profile) and the app lifecycle.

vnc/protocol.lua    RFB 3.8 state machine: version/security handshake, ClientInit,
                          ServerInit, SetPixelFormat, SetEncodings, the server message loop, and
                          the client input messages. Transport agnostic - it never touches a
                          socket.
vnc/encodings.lua   Rectangle decoders: Raw, CopyRect, RRE, Hextile, TRLE, ZRLE, Tight and
                          the DesktopSize pseudo-encoding.
vnc/zstream.lua     Stateful zlib inflate (one stream per RFB zlib stream) - KOReader's
                          ffi/zlib.lua only offers one-shot uncompress().
vnc/des.lua         DES-ECB in FFI, used by VNC Authentication.
vnc/pxfmt.lua       The client pixel format we negotiate, plus the pixel write helpers.
vnc/util.lua        Byte reader/writer for protocol fields, rect unions, UTF-8 splitting.
vnc/keysyms.lua     KOReader key names / characters -> X11 keysyms.
vnc/session.lua     The transport driver: LuaSocket TCP, Wi-Fi, the poll task, tx/rx
                          buffering, attach/detach, reconnect, dirty-rect plumbing.
vnc/framebuffer.lua The remote plane (a TYPE_BBRGB24 BlitBuffer) and the view transform
                          (fit / zoom / pan / draw).
vnc/app.lua         The full-screen viewer widget: canvas, gestures, on-screen keyboard,
                          menu wiring, remote input.
vnc/menu.lua        The in-app menu.
vnc/dialogs.lua     Connection list, per-connection actions, profile editor.
vnc/keyboard.lua    KOReader's VirtualKeyboard wired to RFB key events via a stub inputbox.
vnc/settings.lua    LuaSettings wrapper: profiles + global settings + the server section,
                          including the environment overrides (read once, never persisted).

The server half (the plugin can also serve KOReader's own screen):
vnc/rfbserver.lua   RFB 3.8 *server* state machine, transport agnostic. The mirror of
                          protocol.lua: coroutine, ("need", n) yields. A client's incremental
                          request with nothing to answer is recorded as `held` (its region) and the
                          driver (vnc/server.lua) answers it - when something changed, or when the
                          coalescing deadline passes. The coroutine never suspends for it: that
                          would stop it reading, and the client's keystrokes would queue behind
                          the held request (c1e3806).
vnc/serverenc.lua   Server-side encoders (Raw, RRE, Hextile, ZRLE) and the conversion from
                          whatever BlitBuffer type the screen is to whatever pixel format a
                          client asks for.
vnc/server.lua      The runtime: LuaSocket listener, one protocol instance per client, the
                          poll task, screen capture, dirty rectangles and input injection.
vnc/servermenu.lua  The "VNC server" section of KOReader's Network menu.

tools/mock_vnc_server.py  Test fixture: an RFB 3.8 server in Python (all encodings, both security
                          types, deterministic patterns, logs every client message).
tools/proto_smoke.lua     Headless protocol tests (drives the real protocol stack over TCP).
tools/ui_smoke.lua        Headless UI tests (real plugin, dialogs and viewer widget, no KOReader
                          process, no server).
tools/tight_jpeg.b64      The fixed 32x32 JPEG the mock serves for its Tight JPEG rectangle.
tools/mock_vnc_client.py  An independent Python RFB 3.8 *client* fixture (decodes every encoding
                          itself, can send input) - used to validate the server half against
                          something that is not our own code.
tools/server_smoke.lua    Headless tests for the server: pixel formats, encoders against our own
                          decoders, the protocol against our own client, the real socket path and
                          input injection.


DESIGN NOTES WORTH KNOWING
--------------------------

Protocol concurrency. protocol.lua runs as a coroutine whose transport yields ("need", n) when it
wants bytes; Session is the driver and resumes it once exactly n bytes have arrived. Everything is
therefore single-threaded and there is no blocking read anywhere. The session runs from a
UIManager:scheduleIn poll task with a per-tick byte budget and a per-tick CPU budget (30 ms), so a
large frame cannot block the UI. Exactly one FramebufferUpdateRequest is outstanding at any time,
which is what bounds memory while the viewer is closed but attached.

Detach/attach. Leaving the viewer detaches (unschedules the poll, stops reading, keeps the socket
and the plane). Re-attaching sends a non-incremental request for the whole screen, which is both
the resynchronisation and the way updates pushed while detached are absorbed. Only Disconnect
closes the socket and restores Wi-Fi, and only Wi-Fi that the plugin turned on is turned off.

Settings. There is no schema version and no migration - the plugin has no released file format to
be compatible with. vnc/settings.lua:normalise() just keeps the file in shape on load:
missing global settings get their defaults, unknown keys are dropped, profiles without a usable
name are dropped. One invariant is enforced there too: at most one profile may carry
`autoconnect` (see below), so the first flagged one keeps it and the rest are cleared.
Never add migration code "just in case" before a format has actually shipped.

Taps always click the remote. The plugin ignores KOReader's "activate menu on tap" preference and
opens the menu on a swipe down in KOReader's menu zone instead; under "tap only" the menu would be
unreachable, and intercepting taps would put a dead spot on the remote desktop. See
ViewerApp:init_menu_zones().

Physical keyboard. Printable characters arrive as TextInput events, not as key events, and
SDL 3 only delivers those after Device:startTextInput() ("Text input events are not received by
default", SDL_keyboard.h). KOReader's own callers are its text fields, so the viewer calls
Device:startTextInput() while it is shown (ViewerApp:_ensure_text_input), re-asserts it after one
of its own dialogs (an InputText pairs startTextInput with stopTextInput) and calls
Device:stopTextInput() when it closes. Named keys go out as X11 keysyms; only the Menu key is kept
back (it toggles the in-app menu), and Back leaves the viewer only on devices without a keyboard.

Keyboard placement and zoom. The canvas (ViewerApp:_layout) is the whole widget, except when the
whole remote screen at the current zoom fits in the space the visible on-screen keyboard leaves -
then the canvas is that space, so the view is placed above the keyboard rather than behind it. The
zoom is never changed by that; only the placement. "Fit (with keyboard)" is the mode that fits the
space the keyboard leaves (and therefore follows the keyboard); "Fit screen" fills the screen and
fixed ratios are absolute. Remote:set_canvas() keeps the view's own idea of its space in step,
which matters because set_scale()/zoom_at() clamp and centre against it.

The on-screen keyboard yields to popups. KOReader stacks a non-modal Menu *below* the modal
VirtualKeyboard, so the keyboard would cover a menu's lower half; ViewerApp:evaluate_keyboard()
therefore only shows it while the framebuffer view owns the screen. Popups the plugin opens notify
the viewer directly. Anything else cannot be noticed by repainting - UIManager:_repaint starts at
the topmost full-screen widget, so a widget appearing *above* the viewer never repaints it - hence
the 250 ms re-check (_watch_keyboard_state). That is also why a toast (a Bell notification) is
explicitly flagged `toast = true`: it is allowed to share the screen with the keyboard.

Refreshes, and why a full-screen widget has to ask for them. UIManager:show/close only queue the
refresh the *caller* passed; with no refreshtype they queue nothing at all (`_refresh(nil, ...)`
returns), and the widgets they uncover are merely flagged for repaint. On an LCD that is
invisible - a repaint is the screen - but an e-ink panel only changes where a refresh asked it to,
which is what made the viewer (a full-screen InputContainer that owns a live image) render in
bands, keep the desktop where a menu should be, and leave the file browser off the panel after a
disconnect. The viewer is therefore shown and closed with an explicit `"full"` (main.lua),
onShow() asks for `"full"`, onCloseWidget() ends with `UIManager:setDirty(nil, "flashui")` (a nil
widget and no region mean the whole screen, and it merges with - and dominates - any regional
request queued in the same tick), and every wholesale change (a new connection, a remote resize, a
zoom, the keyboard appearing, a menu opening) goes through ViewerApp:_wholesale_change(): a
full-screen flash, plus `_needs_flash` so the *next* remote frame - the first one carrying the new
geometry's content - is flashed rather than blitted rectangle by rectangle.

Two traps are worth remembering, both verified against core. UIManager:_repaint *does* have a
safety net - if a widget was painted and nothing was queued, it enqueues one full-screen
`"partial"` - but it is skipped whenever *any* refresh is already in the queue; the on-screen
keyboard closing on its own (VirtualKeyboard:onCloseWidget) queues a refresh of just its own area,
and that regional request was enough to leave the freshly painted home screen unpushed (measured:
60 % of the screen; 75 % with a VNC rectangle pending at the same moment). And KOReader's
promotion counter (FULL_REFRESH_COUNT, c.f. UIManager:_refresh) only ever promotes `"partial"`, so
a viewer that refreshes its rectangles with `"ui"` never gets a periodic flash however long it
runs - hence the explicit flush above. `"partial"` itself is deliberately *not* used for the
rectangles: on a REAGL Kindle it is the REAGL waveform, i.e. a flash per rectangle, which is why
ImageViewer uses `"ui"` for the same job.

Platform. Nothing in the plugin is SDL specific: the only input-platform calls are
Device:startTextInput/stopTextInput, and Device:isTouchDevice()/hasKeyboard() are asked rather than
assumed. The single external interface in the whole plugin is zlib: zstream.lua declares z_stream
and inflate*/deflate* and loads the library with ffi.loadlib("z", 1) - the exact call core's
ffi/zlib.lua makes, so the monolibtic redirects (Android, iOS) apply. It deliberately declares only
what ffi/zlib_h.lua does not (that one has compressBound/compress2/crc32/uncompress). DES is
hand-rolled FFI, so there is no libcrypto/OpenSSL dependency, and LuaSocket is used for raw TCP
only (no TLS, so LuaSec is not needed).

Serving KOReader's screen. The listener and the per-client coroutines run from a
UIManager:scheduleIn poll task (the same discipline as the client's socket), and dirty rectangles
come from wrapping a pair of UIManager hooks: `_refresh`, which is where a frame's region becomes
known, and `_repaint`, which is where its pixels reach Screen.bb (it calls every dirty widget's
paintTo and then drains the queue `_refresh` filled). A rectangle is *recorded* only at the end of
the outermost `_repaint` after the `_refresh` that named it - a rectangle is a claim about pixels,
and recording it when `_refresh` is called stamps a generation whose pixels are not in the
framebuffer yet. That is not a theoretical race: input the server injects is delivered from inside
the poll task, so the `_repaint` that paints what it caused runs only after that poll has already
answered the client - the answer carried the frame from *before* the change while sent_gen moved
past it, and the change was lost until a later event recorded another generation (a
keyboard-driven repaint reaching the client one event late; a click escaped it only because the
widgets a click lands on repaint through forceRePaint, which paints inside the injection). Only
rectangles are recorded in either hook; encoding happens in the poll task, so a repaint never pays
for a client's bandwidth. Rectangles carry a generation and each client remembers the one it was
served with, so a client that lagged behind the eviction window is simply given a full frame
instead of a partial one. A screen-size change (rotation) sends every client a DesktopSize
rectangle (-223) and then a full update.

A conversion may be shared only while it is still the encoder's latest. Only `pixels` - an immutable
copy of the rectangle's bytes - may be kept; `values` is the encoder's *single* per-pixel array,
which the next conversion overwrites, so it is handed out only while the owner's convert_serial
still marks it current. Sharing it after another conversion makes every rectangle of a repeated
geometry - KOReader records one click as a "nil" and a "full" refresh of the same region - carry the
last rectangle converted's pixels: a whole region painted with the bottom-right tile's content.

A request that has nothing to answer is *held*, not answered. Answering it with an empty update
looks harmless, but a viewer asks again the moment it is answered: measured with TigerVNC that is a
ping-pong at the poll rate - 97 round trips a second in both directions, ~9 kB/s on the wire, 194
packets/s - for as long as nothing on screen changes. The hold lives in the connection's state
(`client.held`), never in the protocol coroutine: suspending the coroutine would also stop it
reading, and the client's keystrokes would queue behind the held request (c1e3806). The driver
answers it from its poll, when something inside the region changed, and sends one empty update per
Server.HOLD_DEADLINE (1 s) as a sign of life if the client has gone quiet with the request
outstanding - the deadline runs from the client's *latest* request, so a client that keeps asking
while nothing changes is not answered at all. The hold survives that sign of life (the request has
not been answered with content), which is what keeps a viewer that queues several requests - gtk-vnc
sends a dozen at once - receiving changes afterwards. Measured after: 0.91 round trips a second
either way with TigerVNC, a change delivered in ~19 ms while a request was held, and a keystroke
injected in ~9 ms while a request was held.

Client input is injected at the level KOReader's own device backends use: EV_ABS/EV_SYN events
into Device.input:handleTouchEv for pointer events (press/release becomes a tap, a tap-and-move a
drag; there is no multi-touch in VNC), EV_KEY through the device's own event_map for named keys
(so the keysym -> KOReader key name mapping is device independent), and TextInput events for typed
text. VNC Authentication reuses des.lua and mirrors the client's construction exactly.

Injected input must be stamped on the clock the device stamps its own events with (the one
GestureDetector probed; Server:_inject's `at` defaults to it). An event on another clock - os.time()
is CLOCK_REALTIME in whole seconds - arms a hold timer decades away, and while such a timer is
pending Input:waitEvent never returns to UIManager, so the scheduled poll task stops. A client press
must not be injected the moment it is read: a contact that is down starves that same loop, so the
plugin buffers it (Server:_on_pointer) until it is a tap (down+lift, one frame each), a drag (down +
motion past Server.DRAG_THRESHOLD), or a real long press (the bare down, from Server:_flush_pointer
at the detector's own hold interval).

Four LuaSocket traps this hit, worth remembering: receive(n) only returns once it has all n bytes,
so a non-blocking receive of a large chunk always "times out" with the data still in the kernel
(read exactly the bytes the protocol owes, and give the socket a short positive timeout instead of
zero), and a send on a zero-timeout socket can be dropped silently. Both a timed-out receive and a
timed-out send still move bytes, and LuaSocket hands those back only in the third return value
(receive's partial, send's last-byte index): ignoring them silently shifts every later message by
the number of bytes lost, or sends the same bytes twice, while the connection stays up and nothing
works. And RFB pointer input state (buttons, press_x/press_y, dragging) belongs to the input
callback, which has to see the mask as it was *before* the message: storing it in the protocol layer
first makes every press look like motion, so no click is ever injected. Also: FFI arrays are 0-based
while the encoders index pixels 1..count, so the pixel-value array is allocated one slot larger.

Four more lessons the same socket path cost. A FramebufferUpdate is several small writes (the
header, then each rectangle's header and payload), and with Nagle on the server's accepted socket
the later ones wait for the first one's ACK - ~40 ms added to every update, empty answer and fence
reply, until tcp-nodelay is set (Server:_adopt_client; the client half does the same). A poll must
read a whole buffer, not one protocol field: reading exactly the bytes the protocol owed made every
six-byte pointer message cost four poll intervals (~41 ms), so a client's mouse moved at about 24
messages a second. Pure-Lua framing is ~0.3 us per message, so latency was never the interpreter's
fault - it was a syscall per field and a poll interval per message. And a test must never depend on
the server being slow: an incremental request with nothing changed is answered at once, so a check
that "worked" only because the answer took 50 ms is a bug.

The server is off by default; it is started from the Network menu (or at boot by the menu's "Start
with KOReader"), and the menu carries the only UI it has. The boot start is *deferred* to the next
UI loop turn (`UIManager:nextTick`, scheduled from main.lua's init): at init() the screen and input
may not be ready, and starting the server hooks UIManager. It is also scheduled exactly once, so
nothing re-arms it and a manual stop stays a stop until the next KOReader start. A failed boot start
is logged (warn) and left in the server's `last_error`, which the menu's status line shows; boot
pops no dialog.

The client's own "connect at start" is a per-profile `autoconnect` flag with the same deferral
(`VNC:schedule_autoconnect` -> `UIManager:nextTick` -> `VNC:autoconnect_at_boot`, scheduled once
from init()). Only one profile may carry it: `Settings:save_profile` and `Settings:set_autoconnect`
clear it on every other profile when it is set, and `Settings:normalise()` keeps the first flagged
profile and clears the rest on load, so the invariant holds for a hand-edited file too. A failed
boot connect reports itself through `connect_profile` - the same "Could not connect to ..." message
a manual attempt shows - and leaves the normal UI in place; there is no retry. If `start_with`
still names us but no profile is flagged, the boot does nothing and logs a warning.

"Start with". KOReader builds that submenu from a hard-coded list of five values and has no boot
hook and no registry for it: reader.lua's if/elseif chain knows only its own values, and an unknown
one silently opens the file manager. A plugin can still get an entry in, through the generic
`sorting_hint` orphan mechanism - an item carrying `sorting_hint = "start_with"` is nested by
MenuSorter into the submenu whose id is `start_with` (ui/elements/filemanager_menu_order.lua).
Presence has to follow the flag *after* the menu is built (the file-manager menu is cached), so a
`sub_item_table_func` filters the entry out when nothing is flagged - it is absent, not disabled -
and the core label function is wrapped additively, because core's `text_func` returns nil for a
value it does not know and would leave "Start with" with nothing after it. (TouchMenu resolves that
function; the legacy non-touch `Menu` path reads the static table the sorter filled, so there the
entry is unconditional - that path is only for a device with neither touch nor a d-pad.) The
choice itself is stored as `start_with = "vnc_autoconnect"`. Core's boot branch cannot be
intercepted (external plugins are not loaded before FileManager:init), so selecting the entry makes
KOReader open the file manager first and the deferred autoconnect then shows the viewer over it;
that first frame is inherent to doing this without shipping a userpatch. With nothing flagged the
entry is absent, and a stale `start_with` is only logged.

The environment overrides (`VNC_KOPLUGIN_ENABLE_SERVER`, `_SERVER_HOST`, `_SERVER_PORT`,
`_SERVER_PASSWORD`) are parsed once at load in `vnc/settings.lua:read_env`, behind a lookup seam
(a function, `os.getenv` by default) so they are testable without touching the real environment.
They take precedence over the stored server settings for the run but live outside `data.server`:
the running server is built from `Settings:server_for_run()` - the stored table merged with the
overrides (and the stored table itself when there are none) - while `data.server`, which the menu
edits and `flush()` writes, never sees them, so the file stays byte-identical across an exit-time
flush. `VNC_KOPLUGIN_ENABLE_SERVER` decides the boot start in place of the stored `autostart`: empty
is no opinion, the trimmed words `0`/`no`/`false` mean do not start, anything else means start. An
empty `VNC_KOPLUGIN_SERVER_PASSWORD` is a meaningful "no password", so it is kept.

Its Kindle firewall hole follows httpinspector.koplugin (there is no sshd plugin in this KOReader to
follow).

KOReader internals relied on (could change under us): UIManager._window_stack (for "is a popup
above us"), UIManager:scheduleIn/unschedule/nextTick/setDirty, VirtualKeyboard's inputbox protocol
and its showKeyboard/hideKeyboard/setVisibility, Screen:getSize/setRotationMode, the
SetRotationMode/ScreenResize events, DataStorage/LuaSettings, and NetworkMgr. Tools and gestures
use the documented InputContainer APIs (registerTouchZones/updateTouchZonesOnScreenResize,
ges_events with function ranges so they follow rotation without re-registration).

On e-ink the widget colour type may be BB8: the plane is always RGB24, cross-format blits go
through BlitBuffer, and the grey path uses ditherblitFrom when Screen.sw_dithering is on.


TESTS
-----

Protocol layer (needs python3 with the standard library, libcrypto with the legacy provider for the
mock's DES, and KOReader's own LuaJIT):

    PLUGIN=~/.config/koreader/plugins/vnc.koplugin
    cd /usr/lib/koreader && \
      LUA_PATH="$PLUGIN/?.lua;./common/?.lua;./common/?/init.lua;;" \
      LUA_CPATH="./common/?.so;;" \
      ./luajit "$PLUGIN/tools/proto_smoke.lua" --tmp /tmp/vncv_smoke

It starts one mock_vnc_server.py per case on an ephemeral port and drives the real protocol stack
over a real socket: DES against FIPS vectors, the VNC-auth bit reversal, the pixel format and
encoding list as they hit the wire, None/VNC security (including a wrong password), every encoding
decoded pixel-exactly, ZRLE stream continuity across many rectangles, DesktopSize, the exact bytes
of pointer/key/cut-text messages, and the fatal path for an encoding we never advertised. The mock
verifies VNC Authentication with OpenSSL's DES (through ctypes), i.e. with an implementation
independent of vnc/des.lua.

UI plumbing (headless, no KOReader process, no server):

    PLUGIN=~/.config/koreader/plugins/vnc.koplugin
    cd /usr/lib/koreader && \
      KO_HOME=/tmp/vncv_ui_home \
      LUA_PATH="$PLUGIN/?.lua;;" LUA_CPATH="./common/?.so;;" \
      ./luajit "$PLUGIN/tools/ui_smoke.lua"

It builds the real plugin, its dialogs and a real viewer widget against KOReader's widget stack and
checks the flows that are hard to reach by hand: every menu/dialog returns to where it came from,
a failed connection returns to the connection list with exactly one dismissable message, the
canvas follows rotations, the keyboard neither rescales nor moves a view that does not fit above
it, the fitted zoom modes and the keyboard-aware placement behave, the keyboard yields to popups,
platform text input is enabled exactly while the viewer is shown, typed text and physical keys
reach the remote (through KOReader's own SDL event handler), and the settings store survives a
hand-edited or empty file. It also covers the server menu's autostart toggle, the environment
overrides' parsing rules and precedence (through read_env's lookup seam), that a flush after them
leaves the settings file byte-identical, and that the deferred tick starts the server exactly once
when the setting (or the environment) asks for it. The client half gets the same treatment: the
`autoconnect` flag round-trips through the file, survives an edit that does not mention it, clears
any other flagged profile (and a hand-edited file with two is normalised to the first on load), the
actions dialog's switch and the list's marker work, the deferred tick connects the flagged profile
(and nothing when none is flagged, with the network stubbed), a failed boot connect is reported
like a manual one, and the **VNC auto connect** entry is nested into KOReader's **Start with**
submenu by the real MenuSorter only while a profile is flagged (and the stale-setting fallback is
logged). The viewer checks at the end model the *panel*
as well: an e-ink panel is a medium that only changes where a refresh asked it to, so a screen
buffer that was painted but never refreshed is caught as stale pixels (that is the check the
missing `"full"`/`"flashui"` on show/close and the missing flash on a wholesale change used to
fail, with 60 % of the screen left over in the close case). `KO_HOME` is needed because KOReader's
widget cache lives under it.

Server half (headless):

    PLUGIN=~/.config/koreader/plugins/vnc.koplugin
    cd /usr/lib/koreader && \
      KO_HOME=/tmp/vncv_server_home \
      LUA_PATH="$PLUGIN/?.lua;./common/?.lua;./common/?/init.lua;;" LUA_CPATH="./common/?.so;;" \
      ./luajit "$PLUGIN/tools/server_smoke.lua"

It checks the pixel-format packing byte for byte, then round-trips every encoder through the
client's own decoders, then drives the server protocol against the client protocol in process
(including both VNC Authentication outcomes), then the real runtime over a TCP socket (listener,
poll task, capture hook, encode, decode, pixels), and finally that a client PointerEvent becomes a
KOReader gesture.

Live end-to-end (GUI): run the mock, run KOReader, drive the plugin through KOReader's HTTP
inspector (port 8989, httpinspector.autostart = true):

    PLUGIN=~/.config/koreader/plugins/vnc.koplugin
    python3 "$PLUGIN/tools/mock_vnc_server.py" --port 5900 --encoding zrle --pattern quadrants \
        --log /tmp/mock.log &
    koreader &                      # or: env KO_HOME=/tmp/ko_home ./reader.lua
    sleep 20
    curl -s 'http://127.0.0.1:8989/koreader/ui/vnc/connect_profile/local/'
    curl -s 'http://127.0.0.1:8989/koreader/ui/vnc/app/send_pointer/300/200/1'
    curl -s 'http://127.0.0.1:8989/koreader/ui/vnc/app/send_key/65293/1'   # 0xFF0D down
    grep -E 'INPUT (PointerEvent|KeyEvent)' /tmp/mock.log
    curl -s -o /tmp/screen.png 'http://127.0.0.1:8989/koreader/device/screen/bb'

Inspector grammar: a trailing "/" calls a method (arguments are simple values - a string "0" stays
a string, so booleans are awkward), no slash reads a field, and BlitBuffers come back as PNG. It
only reaches objects reachable from the file manager, so it can drive the connection list and the
viewer widget (open_menu/close_menu/zoom_to/set_keyboard_visible/onKbdHide/send_pointer/send_key)
but not the dialogs those open; those flows are covered by ui_smoke.lua. Screenshots are the
evidence for anything visual: the mock's patterns are deterministic, so pixel probes of
device/screen/bb can assert placement and rendering exactly.


WHAT HAS BEEN VERIFIED, AND WHAT HAS NOT
----------------------------------------

Server side, verified live: the server started from the plugin's own API served KOReader's real
1920x1014 screen to tools/mock_vnc_client.py (an independent decoder) as one ZRLE update, and
stopped cleanly. In-process, the same frames are decoded by the plugin's own client protocol and
compared pixel by pixel. Not verified against a third-party VNC viewer (none is installed here)
and not on real e-ink hardware.

Verified on a desktop with the SDL Emulator device, against tools/mock_vnc_server.py:
all seven encodings rendering in the live GUI; pointer, key and text input reaching the server;
the on-screen keyboard overlapping without rescaling, following rotations, yielding to menus and
dialogs, and a view that fits being placed above it; the zoom modes (fit screen / fit with
keyboard / fixed ratios) including their menu labels; detach/keep-alive/reconnect; the Wi-Fi
auto-connect/restore semantics; the grey-screen (BB8) dithering path; and the connection dialogs'
back-flows.

Not verified, and where to look first if something is wrong:

- The gesture *detector*: multi-touch gestures (pinch/spread/rotate/two-finger drag) cannot be
  synthesised on this box (no ydotool/wtype, /dev/uinput is not writable, no bare X server, and
  Xwayland ignores XTest keys for an unfocused window), so the handlers are tested but the wiring
  from real fingers is not. Same for a real tap in the menu zone.
- Tight compression: exercised against the mock only. It is not RFC 6143 and servers differ in how
  they read its control byte (0x0A is "uncompressed" in libvncclient, "PNG" in TurboVNC/noVNC);
  the implementation follows libvncclient, cross-checked against noVNC. Flip the
  ["enable_tight"] default only after a real server has been verified.
- Real e-ink hardware: the BB8/rotation/NetworkMgr paths exist and are exercised in their emulated
  forms only. The emulator cannot show the *effect of a refresh kind* at all - every mode falls
  through to the same refresh implementation there - so "the panel receives a full-screen, flashing
  refresh whenever the whole canvas changes" is asserted by the panel model in ui_smoke.lua, while
  how a given Kindle's EPDC renders that refresh (a partial waveform mishandling a wholesale change
  is what the flicker and the ghosted strips looked like) still needs the device.
- Suspend: while KOReader is suspended the poll task simply does not run and the single
  outstanding update request is buffered by the kernel. If a connection turns out to die across
  suspend, re-requesting a full update on resume is the fix - not implemented.
- TLS/VeNCrypt/SASL servers, and security types other than None/VNC Authentication: unsupported by
  design (the handshake reports them as unsupported).
